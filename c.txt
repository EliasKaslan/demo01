# 概览

大语言模型推理的显存瓶颈主要来自三部分：**模型权重**、**KV Cache**、**运行时激活值**。随着模型规模增长，单张 GPU 已无法容纳完整模型，必须通过多种并行技术将计算与存储分散到多卡 / 多节点。

vLLM 原生支持以下并行/优化维度：**张量并行（TP）、数据并行（DP）、专家并行（EP）、流水线并行（PP）、上下文并行（Prefill CP / Decode CP）**，以及编译期的**序列并行融合（Sequence Parallelism Pass）**。这些维度切分粒度、通信开销、显存收益各不相同，可组合使用以适配不同规模的模型与硬件拓扑。

> **重要说明**：EP 并不是一个独立可设置的"卡数"维度，而是由 `TP_SIZE × DP_SIZE` 自动派生；Decode Context Parallel（DCP）也不会增加总进程/GPU 数，它复用已有的 TP rank。因此计算总卡数时不能简单做 `PP × TP × EP × DP × CP` 的连乘，具体规则见下文各节。

**核心显存计算公式（BF16 精度，标准 MHA/GQA 架构，仅作粗略估算）：**

- 模型权重显存 = 参数量 × 2 Byte
- KV Cache 显存 ≈ 2 × batch_size × seq_len × num_layers × num_kv_heads × head_dim × 2 Byte
  - 第一个系数 2 代表 K、V 两份缓存
  - 第二个系数 2 为 BF16 单元素字节数
  - 标准 MHA 架构下 `num_kv_heads × head_dim = hidden_size`，可简化为 `batch_size × seq_len × hidden_size × num_layers × 4 Byte`
  - **注意**：该公式仅适用于标准 MHA/GQA。对于 MLA（Multi-head Latent Attention，如 DeepSeek-R1/Kimi-K2 系列）架构，KV Cache 被压缩到低秩 latent 空间，实际占用远小于该公式估算值，不能直接套用。
- 激活显存 ≈ 权重显存的 10%~30%（推理阶段，随 batch 与序列长度变化）

# 张量并行 TP

## 原理

张量并行（Tensor Parallelism）是**层内并行**策略：将 Transformer 每一层的权重矩阵（注意力的 Q/K/V/O 投影矩阵、FFN 的门控 / 上 / 下投影矩阵）按行或按列切分到多张 GPU 上，每张卡只持有一部分权重，计算时各自完成分片矩阵乘法，再通过 All-Reduce / All-Gather 集合通信拼合结果。

以线性层 `Y = XA` 为例：

- **列并行**：将 A 按列切分为 `[A₁, A₂]`，各卡独立计算 `XA₁`、`XA₂`，最后沿列维度拼接结果
- **行并行**：将 A 按行切分为 `[A₁; A₂]`，输入 X 对应沿列切分，各卡独立计算后通过 All-Reduce 求和得到最终结果

## 作用

- 解决单卡放不下单层权重的问题，将模型宽度维度（hidden_size）打散
- 同节点内通过 NVLink 高速互联，通信延迟低，效率高
- 降低单卡权重显存，释放更多空间给 KV Cache

## vLLM 中使用方式

```python
from vllm import LLM

# 单节点内 8 卡张量并行
llm = LLM(
    model="model-path",
    tensor_parallel_size=8,
)
```

命令行启动：

```bash
vllm serve model-path --tensor-parallel-size 8
```

## 对显存的影响

- **模型权重**：单卡权重显存 ≈ 总权重显存 / TP
- **KV Cache**：默认按 kv-head 维度分片；当 TP 超过 kv-head 数量时，KV Cache 会在多卡间出现重复（详见下文 Decode Context Parallel 一节）
- **激活值**：中间激活同样按 TP 分片
- **额外开销**：需预留通信缓冲区

> **注意**：TP 依赖高频集合通信，受限于节点内高速互联，通常不建议跨节点使用，实用上限为单节点 GPU 数（如 8 / 16）。

# 数据并行 DP

## 原理

数据并行（Data Parallelism）：每份副本持有**完整的模型权重**（或按 TP 切分后的权重副本），请求按 DP rank 拆分分发，各副本独立完成前向计算。在 vLLM 中，每个 DP rank 对应一个独立的"core engine"进程，与前端 API 进程之间通过 ZMQ 通信。

对于 MoE 模型，DP 和 EP/TP 往往结合使用：可以用 DP 处理注意力层（各 rank 独立），用 TP 或 EP 处理专家层；专家层默认会形成大小为 `DP × TP` 的（张量并行）组，只有显式开启 `--enable-expert-parallel` 才会切换为专家并行组。

## 作用

- 提升推理吞吐量
- 适合高并发、低延迟要求的在线服务场景
- 每个 DP rank 拥有独立的 KV Cache，配合前缀缓存可提高命中率

## vLLM 中使用方式

vLLM 通过 `vllm serve` 命令行自身管理 DP 进程，不需要 `torchrun` 等外部启动器：

```bash
# 单节点 8 卡：DP=4，每副本 TP=2
vllm serve $MODEL --data-parallel-size 4 --tensor-parallel-size 2
```

跨节点部署时，每个节点单独运行一次 `vllm serve`，并指定该节点上的 DP rank 范围：

```bash
# Node 0（IP 10.99.48.128），DP ranks 0-1
vllm serve $MODEL --data-parallel-size 4 --data-parallel-size-local 2 \
                  --data-parallel-address 10.99.48.128 --data-parallel-rpc-port 13345
# Node 1，DP ranks 2-3，headless（不提供 API 端点）
vllm serve $MODEL --headless --data-parallel-size 4 --data-parallel-size-local 2 \
                  --data-parallel-start-rank 2 \
                  --data-parallel-address 10.99.48.128 --data-parallel-rpc-port 13345
```

## 对显存的影响

- **模型权重**：单卡持有权重副本，DP 不降低单卡权重显存（除非结合 TP/EP）
- **KV Cache**：各副本独立维护，系统总 KV Cache 随 DP 线性增长
- **适用场景**：当单副本权重已能放入单卡（或 TP 组），需要提升吞吐时使用

> **关键区别**：TP/EP 是"切分权重大家分着放"，DP 是"每份副本独立持有一份（切分后的）权重"，主要用于扩展系统总吞吐量而非单卡显存。

# 专家并行 EP

## 原理

专家并行（Expert Parallelism）是 **MoE（混合专家）模型专属**的并行维度。MoE 模型每层包含大量独立的 Expert FFN，前向时每个 token 只路由到少数几个专家。EP 将所有 Expert 均匀分布到多张 GPU 上。

计算流程：

1. 路由门控决定每个 token 去往哪些专家
2. 通过 All-to-All 通信将 token 分发到对应专家所在 GPU
3. 各卡独立计算本地专家的 FFN
4. 再次 All-to-All 将计算结果送回原 rank

## 作用

- MoE 模型参数主要集中在专家层，EP 是降低单卡权重显存最直接的手段
- 可与 TP、DP 组合，形成"注意力层 TP/DP + 专家层 EP"的组合并行

## vLLM 中使用方式

EP **不是**一个独立的 `--expert-parallel-size` 参数，而是需要显式打开 `--enable-expert-parallel` 标志；开启后，专家层的并行度自动等于：

```text
EP_SIZE = TP_SIZE × DP_SIZE
```

不开启该标志时，专家层默认仍使用张量并行（组大小同样是 `TP × DP`），只是切分粒度和通信模式不同（All-Reduce vs. All-to-All）。

开启 EP 后，注意力层的行为取决于 TP 大小：`TP=1` 时注意力权重在所有 DP rank 间复制（数据并行）；`TP>1` 时注意力权重在每个 DP 组内做张量并行切分。

```bash
# 单节点 8 卡：TP=1（注意力层复制），DP=8（注意力层数据并行），EP=8（专家层）
vllm serve deepseek-ai/DeepSeek-V3-0324 \
    --tensor-parallel-size 1 \
    --data-parallel-size 8 \
    --enable-expert-parallel
```

跨节点场景需要额外安装 DeepEP/DeepGEMM 等 EP 通信内核，并通过 `--all2all-backend` 选择合适的 All-to-All 后端（如 `deepep_high_throughput`、`deepep_low_latency`、`mori_high_throughput` 等）。

## 对显存的影响

- **专家权重**：单卡专家权重显存 ≈ 总专家权重 / EP_SIZE
- **非专家权重**（注意力、嵌入、共享专家、门控等）：按 TP（或在 TP=1 时复制）切分，与 EP_SIZE 无直接关系
- **通信开销**：每层 MoE 需要两次 All-to-All，通信量与激活 token 数成正比
- 若同时开启 EPLB（专家负载均衡），需额外预留冗余专家的显存开销，约为 `NUM_MOE_LAYERS × BYTES_PER_EXPERT × NUM_REDUNDANT_EXPERTS / NUM_EP_RANKS`

> **核心价值**：对于超大规模 MoE 模型（专家参数占比通常在 90% 以上），EP 是将单卡权重压入有限显存的关键技术。

# 流水线并行 PP

## 原理

流水线并行（Pipeline Parallelism）是**层间并行**策略：将模型按层（Layer）拆分为多个阶段（Stage），每个 GPU 负责连续的若干层。输入数据被拆分为微批次（Micro-batch），像流水线一样依次经过各阶段。

## 作用

- 突破单节点 TP 的规模上限，实现跨节点的超大模型部署
- 通信量远小于 TP（仅传输层间激活，而非每层内部多次集合通信）
- 适合极深模型或跨低带宽节点的场景

## vLLM 中使用方式

```python
from vllm import LLM

llm = LLM(
    model="model-path",
    pipeline_parallel_size=4,
    tensor_parallel_size=8,
)
```

命令行启动（4 阶段流水线 + 8 卡张量并行）：

```bash
vllm serve model-path --pipeline-parallel-size 4 --tensor-parallel-size 8
```

## 对显存的影响

- **模型权重**：单卡权重显存 ≈ 总权重显存 / PP
- **KV Cache**：每阶段只保存自己负责层的 KV Cache，约为总量 / PP
- **额外开销**：需要存储微批次的激活值用于流水线传递
- **副作用**：存在"流水线气泡"，PP 越大气泡占比越高，首 token 延迟上升

> **选型建议**：优先用满节点内 TP，再用 PP 跨节点扩展。

# 上下文并行（Prefill CP / Decode CP）

## 原理

vLLM 中的上下文并行沿**序列长度维度**切分，分为两个独立的机制：

- **Prefill Context Parallel（PCP，`-pcp`）**：面向长序列 Prefill，将 `T` 个新 token 的 Q/K/V 计算切分到 `N` 张 GPU，目标是降低 TTFT（首 token 延迟）。PCP **会**扩展进程数，但不增加 KV Cache 的分片数。目前仍在活跃开发中。
- **Decode Context Parallel（DCP，`-dcp`）**：面向 Decode 阶段，解决 KV Cache 在 TP 维度上的重复问题。当 `TP` 超过模型的 kv-head 数 `H` 时，KV Cache 会重复 `TP/H` 份；DCP 沿 token 维度（`T`）继续切分 KV Cache，采用交错（interleave）布局，配合类 Ring-Attention 的环状通信完成全局注意力计算。**DCP 不增加进程/GPU 总数**，它复用已有的 TP rank，取值范围为 `[1, TP/H]`。

## 作用

- PCP：加速长序列 Prefill，降低首 token 延迟
- DCP：消除/减少 TP 场景下的 KV Cache 重复存储，为更大 batch 或更长上下文腾出显存
- 均不切分模型权重，可与 TP / PP 正交组合

## vLLM 中使用方式

```bash
# TP=16，DCP=16：完全消除单头 MLA 模型（如类 DeepSeek-R1/Kimi-K2 架构）的 KV Cache 重复
vllm serve model-path \
  --tensor-parallel-size 16 \
  --decode-context-parallel-size 16
```

也可以只部分抵消重复（如 `--decode-context-parallel-size 8`），在减少 KV Cache 重复的同时把 DCP 通信限制在单节点内以降低开销。

## 对显存的影响

- **模型权重**：不切分，与 CP 无关
- **KV Cache**：DCP 主要用于**消除因 TP 超过 kv-head 数而产生的重复**，而不是无限度线性缩减；PCP 不改变 KV Cache 分片数
- **通信开销**：DCP 每层注意力需要跨 rank 交换 Q/部分输出及 softmax LSE，通信量随 `dcp_size` 增加而上升

# 序列并行融合（Sequence Parallelism Pass）

## 原理

与前面几种"部署时配置的并行维度"不同，vLLM 中的序列并行是**编译期的图重写优化**（`SequenceParallelismPass`），作用于 TP 场景下的 `AllReduce → RMSNorm` 模式，将其替换为 `ReduceScatter → 本地 RMSNorm → AllGather`，把非注意力的逐元素算子（如 RMSNorm）的输入沿序列维度切分到各 TP rank 上处理，从而消除这些算子在 TP 模式下的重复计算/存储。

该 pass 本身不直接带来性能提升，而是为后续的 **AsyncTP**（`fuse_gemm_comms`，把 GEMM 与 ReduceScatter/AllGather 融合，利用 `torch.ops.symm_mem` 重叠通信与计算）铺路。

## 触发条件

- 仅在全图编译模式下生效：需要 `use_inductor_graph_partition=True`，或 `splitting_ops` 为空（分段编译不支持，因为残差张量会在 TP rank 间被切分，导致子图边界处的尺寸不一致）
- 目前只在 NVIDIA H100/SM90 及以上、且模型 `hidden_size ≥ 8192` 时按 token 数阈值自动开启，阈值可通过 `PassConfig.sp_min_token_num` 配置
- 无需（也没有）额外的环境变量手动开关，由编译优化等级（`-O1` 及以上）和上述条件共同决定

## 对显存的影响

- **模型权重**：无影响，权重仍按 TP 切分
- **激活显存**：非注意力逐元素算子的激活按序列维度分片，可降低该部分的峰值显存
- **KV Cache**：不涉及
- **通信开销**：将原本的 All-Reduce 拆分为 Reduce-Scatter + All-Gather，通信总量相近，但为后续通信-计算重叠创造了条件

# 其它并行与优化技术

## Prefill / Decode 分离部署（PD Disaggregation）

将预填充（Prefill）和解码（Decode）拆分为独立实例分别部署。Prefill 计算密集、KV 写入量大；Decode 访存密集、KV 读取频繁。分离后可各自优化并行配置与硬件选型。

## Expert Parallel Load Balancer（EPLB）

针对 MoE 模型专家负载不均衡的问题，vLLM 提供 EPLB，通过 `--enable-eplb` 开启，周期性根据统计的 token 分布重新映射专家。可配置冗余专家数量（`num_redundant_experts`），但会带来额外显存开销。

# 案例：Kimi-K3模型多机部署显存测算

## 模型参数

| 参数项 | 数值（假设） |
|--------|------|
| 总参数量 | 2.8T |
| 激活参数量 | 约 104B / token |
| 网络层数 | 93 层 |
| 路由专家数 | 896 个 / 层，每 token 选 16 个 |
| 共享专家数 | 2 个 / 层 |
| 权重精度 | BF16 |
| 总权重大小 | 2.8T × 2 Byte ≈ **5.6 TB** |
| 上下文窗口（假设） | 1,048,576 token |

## 硬件配置

- 节点数：16 台，单节点 GPU 数：16 卡，单卡显存：64 GB
- 总卡数：256 卡，总显存：16 TB

## 推荐并行拓扑（PP + TP + EP，DCP 复用 TP rank，不额外占用卡数）

| 并行维度 | 取值 | 说明 |
|----------|------|------|
| PP（流水线并行） | 16 | 跨 16 节点，每节点一个流水线阶段 |
| TP（张量并行） | 2 | 节点内每 2 卡做层内张量切分 |
| DP（数据并行） | 1 | 单副本 |
| EP（专家并行，`--enable-expert-parallel`） | = TP × DP = 2 | **注意**：若要让专家并行度达到 8（如原文设想），需要相应提高 TP 或 DP，例如 `TP=8, DP=1` 才能得到 `EP_SIZE=8`，而不能脱离 TP/DP 单独设置 EP=8 |
| DCP（Decode Context Parallel，复用 TP rank） | ≤ TP/H（H 为 kv-head 数） | 不额外增加卡数，仅用于消除 KV Cache 在 TP 维度的重复 |

**总卡数** = PP × TP × DP = 16 × TP × DP，需要根据目标 EP_SIZE 反推合适的 TP、DP 组合，使 `PP × TP × DP = 256` 且 `TP × DP` 达到期望的 EP 并行度。

## 单卡显存测算（示意，需按最终确定的 TP/DP 重新计算）

### 1. 模型权重显存

**每流水线阶段权重** = 总权重 / PP = 5.6 TB / 16 = **350 GB**

- **非专家部分**（约占 5%）：17.5 GB / 阶段，按 TP 切分
- **专家部分**（约占 95%）：332.5 GB / 阶段，按 EP_SIZE（= TP × DP）切分

### 2. KV Cache 显存

> 若模型采用 MLA 等压缩 KV Cache 的架构，标准 MHA 公式会严重高估实际占用，务必以 vLLM 实测的 `kv_lora_rank`/`qk_rope_head_dim` 等真实维度重新计算，或直接以 vLLM 启动日志中报告的 KV Cache block 数为准。

### 3. 显存汇总与安全边际

- 建议预留 5%~10% 显存余量，设置 `--gpu-memory-utilization 0.9`
- 长上下文场景优先通过 DCP（消除 KV 重复）+ FP8 KV Cache 量化控制显存，而非简单假设"CP 线性缩减总卡数"

# 各并行技术对比总结

| 维度 | 切分对象 | 主要作用 | 单卡权重显存 | 单卡 KV 显存 | 通信开销 | 是否独立增加卡数 |
|------|----------|----------|-------------|-------------|----------|-------------|
| **TP 张量并行** | 层内权重矩阵 | 层内加速、降低单卡权重 | ÷ TP | 依赖 kv-head 数，可能重复 | 高（每层多次 All-Reduce） | 是 |
| **DP 数据并行** | 请求/Batch 维度 | 提升系统总吞吐量 | 不变（不结合 TP/EP 时） | 不变（各副本独立） | 低 | 是 |
| **EP 专家并行** | MoE 专家 FFN | MoE 模型降单卡权重 | 专家部分 ÷ (TP×DP) | 不变 | 中（每层两次 All-to-All） | 否（= TP × DP，需 `--enable-expert-parallel`） |
| **PP 流水线并行** | 层（Layer） | 跨节点扩模型规模 | ÷ PP | ÷ PP | 低（仅阶段间传激活） | 是 |
| **PCP（Prefill CP）** | 序列（Prefill） | 降低长序列 Prefill 的 TTFT | 不变 | 不变 | 中 | 是 |
| **DCP（Decode CP）** | KV Cache（Decode，沿 token 维交错） | 消除 TP 导致的 KV Cache 重复 | 不变 | 减少重复（非线性缩减） | 中（环状/A2A 通信 + softmax LSE 合并） | 否（复用 TP rank） |
| **序列并行融合（Pass）** | 非注意力逐元素算子的激活 | 降低激活显存、为 AsyncTP 铺路 | 不变 | 不变 | 低（Reduce-Scatter+All-Gather 替代 All-Reduce） | 否（编译期优化） |

**选型原则**：

1. 单节点内优先用 **TP** 吃满 NVLink 带宽
2. MoE 模型需要显式加 **`--enable-expert-parallel`** 才能获得专家并行带来的显存/效率收益
3. 跨节点扩展用 **PP**，通信量最小
4. TP 超过 kv-head 数、出现 KV Cache 重复时，加 **DCP** 消除重复；追求超长 Prefill 低延迟时考虑 **PCP**
5. 需要高吞吐量再加 **DP**

# 第二部分　soc_version 参数命名拆分方案（图 2）

## 2.1 一句话结论

把"算子包编译"和"atc 模型编译"两处**同名但取值不同**的 `soc_version` 拆开：前者改名为 `soc_series`，后者保持不变；同时在 CANN 文档中公开"产品系列 ↔ soc_series ↔ soc_version"映射，并提供 npu-smi 查询能力。

## 2.2 现状分析与问题

使用场景：算子包编译、atc 模型编译都需要传入 `soc_version`
- 算子包编译：`soc_version` 与产品系列为 1:1 关系（不区分 PR/DT）
- atc 模型编译：必须包含芯片完整分 bin 信息（芯片全名）

问题：
1. 两处 `soc_version` 同名但取值不同，对用户造成困扰
2. atc 编译需传入芯片全名，枚举值多、易获取性较差、记忆负担重
3. A3 因历史原因，对外模糊处理

## 2.3 三条优化建议

1. **优化 1（规范命名）**：区隔为 `soc_series` 与 `soc_version`，并在 CANN 文档中对外澄清各自的使用场景和获取方式
2. **优化 2（公开映射）**：在 CANN 文档中显式公开产品系列与 `soc_series`、`soc_version` 的映射关系
3. **优化 3（可查询）**：`npu-smi` 新增命令，支持直接查询 `soc_series`、`soc_version`、`NPU_ARCH`，确保开发者有无环境都能获取到这些信息

## 2.4 映射表（核心数据）

| 产品系列 | 算子包编译需传入 `soc_version` → **`soc_series`** | atc 模型编译需传入芯片全名：`soc_version` → **不变** |
| --- | --- | --- |
| 昇腾 960PR / 960DT 系列产品 | `Ascend960PR` / `Ascend960DT`（斜体，规划中） | 遵从昇腾芯片分 bin 命名规范（A3 起实施） |
| 昇腾 950PR / 950DT 系列产品 | `Ascend950` | `Ascend950PR_9589` / `_958b` / `_9579` / `_957b` / `_957c`、`Ascend950DT_9591` / `_9592` / `_9581` / `_9582` / `_9572` / `_9574` 等 |
| 昇腾 A3 系列产品 | `ascend910_93` | `Ascend910_9372` / `_9381` / `_9382` / `_9391` / `_9392` |
| 昇腾 A2 系列产品 | `ascend910b`（\*注 1） | `Ascend910B1` / `B2` / `B3` / `B4` / `B4-1` |
| 昇腾 910 系列产品 | `ascend910` | `Ascend910A` / `Ascend910ProA` / `Ascend910PremiumA` / `Ascend910B` / `Ascend910ProB` |
| 昇腾 310P 系列产品 | `ascend310p` | `Ascend310P1` / `P3` / `P5` / `P7` |
| 昇腾 310B 系列产品 | `ascend310b` | `Ascend310B1` / `B2` / `B3` / `B4` |
| 昇腾 310 系列产品 | NA，不在开源开放范围 | NA，不在开源开放范围 |

## 2.5 三条配套注记（重要约束）

- **新代际**：950 及后续代际按规范设置，`soc_series`、`soc_version` **首字母大写**（故为 `Ascend950`，区别于存量的 `ascend910_xx` 小写风格）
- **存量**：A3 及以前**建议维持不变**，避免反复适配（改动成本优先于命名一致性）
- **注 1**：CANN 文档公开 `soc_series` 取值后，会**间接露出 910B**，需评估影响（未公开芯片名的信息披露风险）

## 2.6 页面标题体现的两点意图

- 参数命名要**区隔**，并在文档中**澄清适用场景**与获取方式
- 历代取值要**跟随产品名/芯片名一起对外公开**，即命名规范与公开口径一并定下来，而不只是改个参数名

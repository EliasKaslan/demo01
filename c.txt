## 1. 为什么要有 V1：一次彻底的架构重写

vLLM V0 架构（`LLMEngine` + `AsyncLLMEngine`）在 2023~2024 年统治了开源推理生态，但它有三个结构性瓶颈：

| V0 痛点 | 具体表现 | V1 解法 |
|---|---|---|
| **单进程耦合** | API 处理、调度、前后处理与 GPU 执行在同一个（异步）进程里，GIL 与 CPU 前后处理阻塞 GPU | **EngineCore 独立进程**，前端与核心引擎经 ZMQ 通信，tokenize/detokenize 与 GPU 计算真正并行 |
| **prefill/decode 两阶段调度** | 先集中 prefill 再切 decode，decode 被 prefill 阻塞，TTFT/ITL 抖动大 | **统一调度**：每个请求只维护 `num_computed_tokens`，调度器每步把它向 `num_tokens_with_spec` 推进，prefill/decode 天然同框（Chunked Prefill 自然支持） |
| **每步全量传输** | 每次调度都序列化完整请求对象给 Worker | **差量传输**：首次传全量，后续只传新增 block id / token id |

V1 从 2025 年初 alpha 起逐步成为默认引擎（`vllm/v1/` 目录），到本文分析的 v0.26.0，V1 已经完全成熟并独占主线：**`vllm/engine/` 只剩 `arg_utils.py` 等配置壳，真正的引擎全部在 `vllm/v1/`**。

```mermaid
flowchart LR
    subgraph V0["V0 时代（旧）"]
        A1["AsyncLLMEngine<br/>(单进程 asyncio)"] --> A2["LLMEngine"]
        A2 --> A3["Scheduler<br/>(prefill/decode 两态)"]
        A3 --> A4["GPUExecutor"]
        A4 --> A5["Worker/ModelRunner"]
    end
    subgraph V1["V1 时代（现行）"]
        B1["AsyncLLM / LLM<br/>(前端进程)"] -->|"ZMQ<br/>(EngineCoreClient)"| B2["EngineCore<br/>(独立进程)"]
        B2 --> B3["Scheduler<br/>(统一 token 预算)"]
        B2 --> B4["Executor"]
        B4 --> B5["Worker × N<br/>(每卡一进程)"]
        B5 --> B6["GPUModelRunner"]
    end
    V0 -.->|"架构重写"| V1
```

**一句话记忆 V1**：`前端进程（tokenize/detokenize） --ZMQ--> EngineCore 进程（Scheduler + KV Cache 管理） --> Worker 进程（ModelRunner + 模型前向 + 采样）`。

### 2.2 进程模型（在线服务部署视角）

V1 是**多进程**架构。以 `vllm serve` 启动 TP=2 为例，真实进程拓扑如下：

```mermaid
flowchart TB
    subgraph P0["进程 0：API Server（前端）"]
        UV["uvicorn/fastapi<br/>entrypoints/openai/api_server.py"] --> ASYNCLLM["AsyncLLM<br/>v1/engine/async_llm.py"]
        ASYNCLLM --> INP["InputProcessor（tokenize）"]
        ASYNCLLM --> OUTP["OutputProcessor（detokenize）<br/>+ 后台 output_handler 线程"]
    end

    subgraph P1["进程 1：EngineCore（引擎核心，busy-loop）"]
        direction TB
        T1["input 线程（ZMQ DEALER 收请求）"]
        T2["output 线程（ZMQ PUB 发结果）"]
        T3["主线程：busy-loop<br/>EngineCore.step()"]
        T1 --> Q1[/"input_queue"/]
        Q1 --> T3
        T3 --> Q2[/"output_queue"/]
        Q2 --> T2
        T3 --> SCH["Scheduler"]
    end

    subgraph P2["进程 2：TP rank0 Worker"]
        W0["WorkerWrapperBase → Worker<br/>(GPU0)"]
    end

    subgraph P3["进程 3：TP rank1 Worker"]
        W1["WorkerWrapperBase → Worker<br/>(GPU1)"]
    end

    ASYNCLLM <-->|"ZMQ: EngineCoreRequest<br/>(msgpack 序列化)"| T1
    T2 -->|"ZMQ: EngineCoreOutputs"| OUTP
    T3 -->|"SchedulerOutput"| W0
    T3 -->|"SchedulerOutput 广播"| W1
    W0 <-.->|"NCCL/HCCL 集合通信"| W1
```

> 三个进程的分工要点：
> - **API Server 进程**：HTTP/WebSocket、参数校验、**tokenize 与 detokenize 都在前端**（CPU 密集，与 GPU 解耦）；
> - **EngineCore 进程**：一个 Python 进程跑 `busy-loop`（`EngineCoreProc.run_engine_core`，见 `v1/engine/core.py`），内部有 input/output 两条后台线程专门做 ZMQ 收发与序列化，主线程纯调度；
> - **Worker 进程**：每个 GPU/NPU 一个进程（由 `MultiprocExecutor` spawn），加载权重、执行前向。进程间通过 `init_process_group` 建立 NCCL（NPU 上是 HCCL）通信。

EngineCoreClient 的三种形态（`vllm/v1/engine/core_client.py`）决定了部署形态：

| Client 类 | 模式 | 场景 |
|---|---|---|
| `InprocClient` | 同进程直调 | 离线 `LLM()`（默认 `multiprocess_mode=False` 时的兼容路径） |
| `SyncMPClient` | ZMQ + 后台进程（同步） | 离线 `LLM()` 的新路径 |
| `AsyncMPClient` | ZMQ + 后台进程（asyncio） | 在线 `vllm serve` / `AsyncLLM` |

## 3. 核心组件逐一拆解

### 3.1 前端：LLM 与 AsyncLLM

两个前端类共享同一套后端，区别只在同步/异步与进程模式：

| | `LLM`（`entrypoints/llm.py`） | `AsyncLLM`（`v1/engine/async_llm.py`） |
|---|---|---|
| 用法 | 离线批量推理 `llm.generate()` | 在线服务（`vllm serve` 内部） |
| 引擎 | `LLMEngine`（`v1/engine/llm_engine.py`） | 直接持有 `AsyncLLM` |
| EngineCore 客户端 | `SyncMPClient` / `InprocClient` | `AsyncMPClient` |
| 输出方式 | 同步收集 `RequestOutput` | `AsyncGenerator[RequestOutput]` |

`AsyncLLM` 内部结构要点（对照 `async_llm.py`）：

- `generate()` / `add_request()` → **`InputProcessor`**（tokenize + 多模态预处理）→ 得到 `EngineCoreRequest` → 经 `EngineCoreClient` 发给 EngineCore 进程；
- 同时为每个请求创建 **`RequestOutputCollector`**（`output_processor.py`），这是一个小的"输出信箱"；
- 一个后台线程 **`_run_output_handler()`** 持续从 EngineCore 拉 `EngineCoreOutputs`，交给 **`IncrementalDetokenizer`** 增量解码、**`OutputProcessor`** 做停止条件判断/日志概率整理，再塞进每个请求的 collector，唤醒对应的 asyncio 任务。

```mermaid
flowchart LR
    U["用户/HTTP"] --> AR["AsyncLLM.add_request()"]
    AR --> IPX["InputProcessor<br/>tokenize / mm 预处理"]
    IPX --> REQ["EngineCoreRequest"]
    REQ --> EC["EngineCore 进程"]
    EC --> OUT["EngineCoreOutputs"]
    OUT --> OH["_run_output_handler 线程"]
    OH --> DT["IncrementalDetokenizer<br/>detokenizer.py"]
    DT --> OPP["OutputProcessor<br/>stop/finish 判断"]
    OPP --> COLL["RequestOutputCollector"]
    COLL -->|"asyncio 唤醒"| STREAM["StreamingResponse"]
```

### 3.2 EngineCore：引擎心脏（`v1/engine/core.py`）

`EngineCore` 是"调度 + 执行"的合体，它的 `__init__` 顺序本身就是一份架构清单：

```python
# vllm/v1/engine/core.py（节选，注释为本文所加）
class EngineCore:
    def __init__(self, vllm_config, executor_class, log_stats, ...):
        load_general_plugins()                      # ① 加载 vllm.general_plugins 插件
        self.model_executor = executor_class(...)   # ② 创建 Executor（拉起 Worker 进程）
        kv_cache_config = self._initialize_kv_caches(vllm_config)  # ③ 显存 profile → KV Cache 规划
        self.structured_output_manager = ...        # ④ 结构化输出管理器
        Scheduler = vllm_config.scheduler_config.get_scheduler_cls()
        self.scheduler = Scheduler(...)             # ⑤ 调度器（可被 vllm-ascend 换成定制调度器）
        ...
```

**主循环 `step()`**（`core.py:576`）——这是整个 V1 最重要的一段代码：

```python
def step(self) -> tuple[dict[int, EngineCoreOutputs], bool]:
    if not self.scheduler.has_requests():           # 无请求直接空转返回
        return {}, False
    scheduler_output = self.scheduler.schedule(...) # 1) 调度：产出一批 token 的执行计划
    future = self.model_executor.execute_model(scheduler_output, non_block=True)  # 2) 异步下发执行
    grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)         # 3) 语法约束位掩码
    model_output = future.result()                  # 4) 等待 ModelRunnerOutput（logits→采样后 token）
    self._process_aborts_queue()                    # 5) 处理执行期间的 abort
    engine_core_outputs = self.scheduler.update_from_output(scheduler_output, model_output)  # 6) 状态推进
    return engine_core_outputs, ...
```

对应的循环驱动在 `EngineCoreProc.run_engine_core`（同文件）：`while True: outputs = self.step(); self.emit(outputs)`——一个不眠不休的 busy-loop，空闲时也每步轮询（保证最低调度延迟）。

```mermaid
flowchart TD
    LOOP["EngineCore busy-loop<br/>run_engine_core()"] --> HAS{"scheduler.has_requests()?"}
    HAS -->|否| IDLE["空转（等待新请求）"] --> LOOP
    HAS -->|是| S1["① scheduler.schedule()<br/>产出 SchedulerOutput<br/>（新 token 数 / block 表 / 抢占列表）"]
    S1 --> S2["② executor.execute_model(scheduler_output)<br/>广播给所有 Worker 进程"]
    S2 --> S3["③ scheduler.get_grammar_bitmask()<br/>(结构化输出约束)"]
    S3 --> S4["④ future.result()<br/>等待 ModelRunnerOutput<br/>（含 sampled_token_ids）"]
    S4 --> S5["⑤ 处理 abort 队列"]
    S5 --> S6["⑥ scheduler.update_from_output()<br/>· KV block 落账<br/>· 请求状态推进（finished?）<br/>· 产出 EngineCoreOutputs"]
    S6 --> S7["⑦ output 线程 ZMQ 发回前端"]
    S7 --> LOOP
```

### 3.3 Scheduler：统一调度器（`v1/core/sched/scheduler.py`）

V1 调度器的**核心思想只有一句话**（源码注释原话，`scheduler.py:427`）：

> "There's no 'decoding phase' nor 'prefill phase' in the scheduler. Each request just has the `num_computed_tokens`. At each step, the scheduler tries to assign tokens to the requests so that each request's `num_computed_tokens` can catch up its `num_tokens_with_spec`."

即：**调度器不做"阶段"管理，只做"token 预算分配"**。每个 step 把 `max_num_batched_tokens` 的预算切给若干请求——正在 prefill 的请求拿到大块 token（chunked prefill），正在 decode 的请求每次拿 1 个（或 spec decode 的 k+1 个）。

```mermaid
flowchart TD
    START["schedule() 每 step 调用"] --> BUDGET["token_budget = max_num_batched_tokens<br/>block 预算 = KVCacheManager 剩余块"]
    BUDGET --> RUN["第一优先级：遍历 running 队列<br/>（已在跑的请求，含 chunked prefill 中途的请求）"]
    RUN --> NEED{"num_tokens_with_spec −<br/>num_computed_tokens > 0 ?"}
    NEED -->|是| ALLOC["分配 min(需求, token_budget) 个 token<br/>调用 kv_cache_manager 分配块<br/>（prefix cache 命中则复用已有块）"]
    NEED -->|否| SKIP["跳过（本轮无需计算）"]
    ALLOC --> CHK{"token_budget 或<br/>KV 块耗尽？"}
    CHK -->|KV 块不足| PREEMPT["抢占：recompute 模式<br/>把最后的请求踢回 waiting<br/>（_preempt_request）"]
    CHK -->|token 预算还有| WAIT["第二优先级：从 waiting 队列<br/>准入新请求（准入条件：KV 够放 prompt）"]
    PREEMPT --> WAIT
    WAIT --> ASSEMBLE["组装 SchedulerOutput：<br/>· scheduled_new/resumed/running_reqs<br/>· num_scheduled_tokens[]<br/>· block_tables[]（新分配块 id）<br/>· total_num_scheduled_tokens"]
    ASSEMBLE --> DONE["返回给 EngineCore"]
```

请求状态机（`v1/request.py` 的 `RequestStatus`）：

```mermaid
stateDiagram-v2
    [*] --> WAITING: add_request()
    WAITING --> RUNNING: 调度准入（prompt 首块分配）
    RUNNING --> RUNNING: 每 step 推进 num_computed_tokens
    RUNNING --> PREEMPTED: KV 不足被抢占
    PREEMPTED --> WAITING: 重新排队（recompute）
    RUNNING --> FINISHED_STOPPED: 满足 stop 条件
    RUNNING --> FINISHED_LENGTH: 达到 max_tokens
    RUNNING --> FINISHED_ABORTED: 客户端 abort
    FINISHED_STOPPED --> [*]
    FINISHED_LENGTH --> [*]
    FINISHED_ABORTED --> [*]
```

### 3.4 KV Cache 管理（`v1/core/`）

V1 的 KV Cache 管理是一套精美的"三级分权"结构：

| 组件 | 文件 | 职责 |
|---|---|---|
| **KVCacheManager** | `v1/core/kv_cache_manager.py` | 门面：请求级语义（"为这个请求分配 n 个块"），内部按 group 委托给 Coordinator |
| **KVCacheCoordinator** | `v1/core/kv_cache_coordinator.py` | 编排多种 KVCacheSpec 类型（full attention / sliding window / mamba / cross...），每组一个 SingleTypeKVCacheManager |
| **BlockPool** | `v1/core/block_pool.py` | 物理块池：空闲块分配、**prefix caching 的哈希表**（block hash → 物理块）、块引用计数 |
| **SingleTypeKVCacheManager** | `v1/core/single_type_kv_cache_manager.py` | 单一类型缓存的管理策略（分配/释放/滑动窗口推进） |

**块（Block）模型**：KV Cache 被切成固定大小的块（如 16/32/128 token 每块，`CacheConfig.block_size`），每个请求有一张 `block_table`（块 id 列表）。这继承自 PagedAttention 思想，但 V1 把"逻辑块/物理块"简化成了"请求 → 物理块表"单层映射。

**Prefix Caching**：以块为单位计算 hash（block 内 token 序列 + 前缀块 hash 链式），相同前缀（典型：system prompt / few-shot）的请求直接复用物理块（引用计数 +1），免算 prefill。由 `CacheConfig.enable_prefix_caching` 开关（V1 默认开启）。

```mermaid
flowchart LR
    subgraph Manager["KVCacheManager (kv_cache_manager.py)"]
        CO["KVCacheCoordinator"]
    end
    CO --> G1["FullAttentionManager<br/>(single_type_kv_cache_manager.py)"]
    CO --> G2["SlidingWindowManager"]
    CO --> G3["MambaManager (mamba_utils.py)"]
    CO --> G4["CrossAttentionManager"]
    G1 --> BP["BlockPool (block_pool.py)<br/>· free_block_queue 空闲链表<br/>· cached_block_hash: 前缀哈希表<br/>· ref_cnt 引用计数"]
    G2 --> BP
```

### 3.6 Attention 后端抽象（`v1/attention/`）

Attention 是推理引擎最核心的可变点（FlashAttention/FlashInfer/MLA...），V1 用经典的三件套抽象：

## 5. 关键机制深潜

### 5.1 Chunked Prefill：长 prompt 切片与混合批

V1 默认 `enable_chunked_prefill=True`：一个长 prompt 会被切成多个 chunk 跨多次迭代计算，且**与 decode 混在同一个 batch**里跑——这靠统一调度器天然实现（对调度器而言 chunked prefill 请求只是一个"每步要很多 token"的 running 请求）。

```mermaid
flowchart TD
    subgraph Step_n["Step n（max_num_batched_tokens=8192）"]
        R1["Req A（prefill中，还剩6000 token）"]
        R2["Req B（decode，需1 token）"]
        R3["Req C（decode，需1 token）"]
        P["调度器分配：<br/>A←6000, B←1, C←1<br/>剩余预算2190可再准入新请求" ]
    end
    Step_n --> Step_n1["Step n+1：A 还剩的部分继续<br/>（A.is_prefill_chunk=True）<br/>B/C 各得1 token…" ]
    Step_n1 --> DONE["A 的 prompt 计算完毕后<br/>转入decode：每步1 token"]
```

好处：decode 请求不再被长 prefill 独占阻塞（ITL 稳定），同时 GPU 每步都有大 batch 可跑（吞吐不掉）。代价：TTFT 略增，可用 `--long-prefill-token-threshold` 等参数调节。

### 5.2 Prefix Caching：块级前缀复用

```mermaid
flowchart TD
    REQ["新请求：prompt = [sys, 5000] + [user, 20]"]
    REQ --> HASH["逐块计算 BlockHash：<br/>hash(块内容, 前块hash, extra) <br/>(core/kv_cache_utils.py)"]
    HASH --> LOOKUP["BlockPool.cached_block_hash 查询"]
    LOOKUP -->|"前 312 块全部命中"| REUSE["直接复用物理块（ref_cnt+1）<br/>num_computed_tokens += 4992"]
    LOOKUP -->|"尾部块未命中"| ALLOC2["只为剩余 8 token 分配新块" ]
    REUSE --> ALLOC2
    ALLOC2 --> FWD["本次 forward 只算 8 个 token！<br/>（TTFT 大幅下降）"]
    FWD -.->|"请求结束"| EVICT["块引用计数-1；归零且被新块挤兑时<br/>按 LRU 逐出哈希表" ]
```

### 5.3 torch.compile 与 CUDA Graph（GPU 路径）

V1 的编译体系（`vllm/compilation/` + `config/compilation.py`）分两层：

- **piecewise torch.compile**：`CompilationMode` 支持 `FULL` / `PIECEWISE`（默认）。PIECEWISE 把模型图在 `splitting_ops`（attention 等）处切开，attention 之外的子图用 Inductor 编译，attention 保留 eager（后端相关）；
- **CUDA Graph**：对 decode 小 batch 的整图捕获重放（`cudagraph_mode`: FULL / PIECEWISE / NONE），消除 Python/kernel launch 开销。

昇腾路径对这两层都有对应实现（AscendCompiler + ACLGraph），见 6.8。

### 5.4 投机解码（`v1/spec_decode/`）

V1 的 spec decode 是"调度器原生"的：draft token 直接计入 `num_tokens_with_spec`，一次 step 验证 k 个草稿 token（目标模型 forward k+1 个 token），再用 `RejectionSampler`（`v1/sample/rejection_sampler.py`）接受/拒绝。支持 EAGLE/MTP/ngram/dflash 等多种 proposer，接口在 `spec_decode/` 各 proposer 文件。vllm-ascend 全套适配了这条链路（`vllm_ascend/worker/v2/spec_decode/` 有原生实现）。

前面五章把 vLLM 主干讲完了，其中埋了三处伏笔：**worker_cls 字符串解析**（3.5）、**attention 后端选择钩子**（3.6）、**平台层 current_platform**（3.7）。vllm-ascend 的全部魔法，就是沿着这三条（以及更多）官方预留的扩展点，把执行层换成昇腾 NPU 实现，而**调度、KV Cache 管理、前端 API 全部复用 vLLM 主干**。

### 6.1 vllm-ascend 与 vLLM 的关系：插件式共生

vllm-ascend 是 vLLM 官方社区维护的**昇腾 NPU 硬件插件**（Out-Of-Tree 插件），版本号与 vLLM 严格对齐（如 vllm-ascend v0.9.1 对应 vLLM v0.9.1）。本文分析的 main 分支即 v0.26 开发版，依赖 torch 2.10 + torch-npu 2.10 + CANN 工具链（见 `vllm-ascend/pyproject.toml`）。

用户侧体验极其简单：

```bash
pip install vllm==0.26.0
pip install vllm-ascend   # 装完即生效，无需改任何启动命令
vllm serve Qwen/Qwen3-32B --tensor-parallel-size 8
```

不需要传 `--device npu`，不需要改 API——安装即接入。这背后是 Python 标准的 **entry_points 发现机制**。

### 6.2 第一步：entry_points 注册（安装期）

`vllm-ascend/setup.py:518`：

```python
setup(
    name="vllm-ascend",
    entry_points={
        "vllm.platform_plugins": [          # ← 平台插件组：决定 current_platform
            "ascend = vllm_ascend:register",
        ],
        "vllm.general_plugins": [            # ← 通用插件组：随各进程启动加载
            "ascend_kv_connector = vllm_ascend:register_connector",
            "ascend_model_loader = vllm_ascend:register_model_loader",
            "ascend_service_profiling = vllm_ascend:register_service_profiling",
            "ascend_model = vllm_ascend:register_model",
        ],
        "ms_service_metric.providers": [     # ← 昇腾可观测性生态
            "vllm-ascend = vllm_ascend.observability:get_metric_provider",

```

`pip install` 后，这些声明被写进该包的 dist-info 元数据。vLLM 侧对应的消费端是 `vllm/plugins/__init__.py` 的 `load_plugins_by_group()`（importlib.metadata.entry_points 扫描），vLLM 预定义了五个插件组：

| 插件组（vllm/plugins/__init__.py） | 加载时机 | vllm-ascend 注册的入口 | 用途 |
|---|---|---|---|
| `vllm.platform_plugins` | 首次访问 current_platform | `register` → 返回 NPUPlatform 类名 | **接管整个平台层** |
| `vllm.general_plugins` | 每个进程启动（EngineCore/Worker） | `register_connector` 等 4 个 | KV 迁移连接器、网络加载器、性能采集、模型注册 |
| `vllm.io_processor_plugins` | 仅前端进程 | — | 输入/输出处理器扩展 |
| `vllm.stat_logger_plugins` | 仅 serve 异步模式 | — | 自定义统计日志 |
| `vllm.endpoint_plugins` | 仅 API Server 前端 | — | 额外 HTTP 路由 |

而 `vllm_ascend/__init__.py:68` 的 `register()` 一行就完成了"亮明身份"：

```python
def register():
    """Register the NPU platform."""
    return "vllm_ascend.platform.NPUPlatform"
```

> 控制反转（IoC）：vLLM 不 import vllm-ascend，vllm-ascend 也不改 vLLM 源码。双方只约定"组名 + 返回类全名"这一契约。

### 6.6 第五步：Attention 后端接管

模型每个 Attention 层在初始化时都会调 `get_attn_backend()`（`vllm/v1/attention/selector.py:101`），它最终落到 `current_platform.get_attn_backend_cls()`。NPUPlatform 的实现（`platform.py:217`）是一个按"模型注意力形态"查表的映射：

```python
# vllm_ascend/platform.py:217（节选）
@classmethod
def get_attn_backend_cls(cls, selected_backend, attn_selector_config, num_heads=None):
    if _validate_fa3_backend(key, attn_selector_config):
        return "vllm_ascend.attention.fa3_v1.AscendFABackend"     # FlashAttention3 形态
    backend_map = {
        (True,  False, False): "vllm_ascend.attention.mla_v1.AscendMLABackend",       # MLA（DeepSeek系）
        (False, False, False): "vllm_ascend.attention.attention_v1.AscendAttentionBackend",  # GQA/MHA
        (True,  True,  False): "vllm_ascend.attention.sfa_v1.AscendSFABackend",       # 稀疏注意力
        (True,  False, True):  "vllm_ascend.attention.dsa_v1.AscendDSABackend",       # DSA（DeepSeek V4）
    }
    if is_310p():  # Atlas 300I Duo 走专用实现
        return "vllm_ascend._310p.attention.attention_v1.AscendAttentionBackend310"
    return backend_map[(use_mla, use_sparse, use_compress)]
```

### 6.7 第六步：算子生态全面接管

vLLM 的模型层算子（RMSNorm/RoPE/ MoE/量化...）都走 `torch.ops.vllm::*` 自定义算子系统。vLLM 预留了"同名替换"机制：每层 Op 声明名与实现分离，平台可通过 `Platform.import_kernels()` 导入自己的算子库覆盖同名 op。vllm-ascend 的对应实现：

| 算子类别 | vllm-ascend 位置 | 说明 |
|---|---|---|
| 自定义算子注册 | `vllm_ascend/ops/__init__.py` + `csrc/ascend/` | C++/Ascend C 实现，注册为 `torch.ops.vllm_ascend::*`；配置期 `custom_ops=["all"]` 后由 `register_ascend_customop()` 全量映射 |
| Flash Attention | `torch_npu.npu_fusion_attention` | ACL 原生算子（attention_v1.py 内直接调用） |
| 量化 | `vllm_ascend/quantization/`（w8a8/w4a4/fp8/mxfp4...） | 实现 vLLM QuantizationMethod 接口 |
| MoE | `vllm_ascend/ops/fused_moe/` | MC2 通信融合、fused MoE kernel |
| 集合通信 | `vllm_ascend/distributed/device_communicators/npu_communicator.py` | HCCL（由 `get_device_communicator_cls()` 返回） |
| LoRA | `vllm_ascend/lora/punica_npu.py` | `get_punica_wrapper()` 返回 PunicaWrapperNPU |
| KV Cache 布局 | `vllm_ascend/core/kv_cache_interface.py` | `register_custom_kv_cache_specs()`：注册昇腾专用 KVCacheSpec（如 NZ 排布、GQA 分离 K/V 池） |

### 6.9 第八步：运行时补丁（Monkey Patch）与 general_plugins

并非所有差异都能通过官方钩子解决（vLLM 迭代快，部分内部行为对 OOT 插件不透明）。vllm-ascend 的兜底手段是"补丁模块"：

```python
# vllm_ascend/utils.py:529
def adapt_patch(is_global_patch: bool = False):
    if is_global_patch:
        from vllm_ascend.patch import platform   # 引擎/调度层补丁（所有进程）
    else:
        from vllm_ascend.patch import worker     # worker 层补丁（worker 进程）
```

补丁目录（`vllm_ascend/patch/`）按进程角色分两组：

- **platform 组**（`patch/platform/`）：修补调度/引擎相关——如 `patch_kv_cache_coordinator.py`（昇腾 KV 布局协调）、`patch_multiproc_executor.py`（进程启动参数）、`patch_distributed.py`、`patch_fused_moe.py`、`patch_torch_accelerator.py` 等 20+ 个；
- **worker 组**（`patch/worker/`）：修补模型执行层——如 `patch_cudagraph.py`、`patch_bind_kv_cache.py`、各模型专用 patch（`patch_qwen3vl.py` / `patch_deepseek_v2.py`...）。

加上 `vllm.general_plugins` 组里注册的四个入口（在 EngineCore/Worker 进程启动时被 `load_general_plugins()` 调用，见 `v1/engine/core.py:110`）：

| 入口函数 | 位置 | 作用 |
|---|---|---|
| `register_connector()` | `__init__.py:74` | 注册 P/D 分离 KV 迁移连接器与权重传输引擎 |
| `register_model_loader()` | `__init__.py:84` | 注册网络流式/RFork 权重加载器 |
| `register_service_profiling()` | `__init__.py:94` | 生成昇腾服务化 profiling 配置 |
| `register_model()` | `__init__.py:102` | 注册 vllm-ascend 的模型实现/补丁 |

## 7. 端到端全景：一次 NPU 上的推理迭代

把第 4 章的"通用时序"与第 6 章的"替换链"叠加，就是用户在昇腾集群上 `vllm serve` 的真实运行图景：

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户端
    participant API as API Server进程<br/>(vLLM主干)
    participant FE as AsyncLLM + InputProcessor<br/>(vLLM主干, 前端)
    participant EC as EngineCore进程<br/>(vLLM主干)
    participant SC as Scheduler<br/>(vLLM主干 / 或vllm-ascend增强调度器)
    participant MP as MultiprocExecutor<br/>(vLLM主干)
    participant W0 as NPUWorker rank0<br/>(vllm-ascend)
    participant W1 as NPUWorker rank1<br/>(vllm-ascend)

    Note over EC,W1: ── 启动期（一次性） ──
    EC->>MP: Executor.get_class()
    MP->>W0: spawn NPUWorker(worker_cls字符串解析)
    MP->>W1: spawn NPUWorker
    W0->>W0: adapt_patch + 算子注册 + HCCL初始化
    W0->>W0: load_model（权重/量化） + profile_run
    EC->>W0: KV Cache 规划 + initialize_from_config
    W0->>W0: initialize_kv_cache（昇腾布局）<br/>+ ACLGraph 捕获

    Note over C,W1: ── 服务期（每个 step 循环） ──
    C->>API: HTTP 请求
    API->>FE: generate() → tokenize
    FE->>EC: ZMQ: EngineCoreRequest
    EC->>SC: add_request
    SC->>SC: schedule()（统一token预算）
    EC->>MP: execute_model(SchedulerOutput)
    MP->>W0: 广播
    MP->>W1: 广播
    par rank0
        W0->>W0: NPUModelRunner：prepare_inputs<br/>→ ACLGraph replay / torch_npu forward<br/>→ AscendAttention（npu_fusion_attention）<br/>→ Sampler → ModelRunnerOutput
    and rank1
        W1->>W1: 同样流程（张量并行切片）
    end
    W0->>W1: HCCL all-reduce / all-gather（集合通信）
    W1-->>W0: 结果汇聚
    W0-->>EC: ModelRunnerOutput（首 rank 汇聚）
    EC->>SC: update_from_output()
    EC-->>FE: ZMQ: EngineCoreOutputs
    FE->>FE: 增量 detokenize + stop 判断
    FE-->>API: RequestOutput
    API-->>C: SSE 流式返回
```

## 附录：术语速查

| 术语 | 含义 |
|---|---|
| TTFT / ITL | Time To First Token / Inter-Token Latency（首 token 延迟/逐 token 间隔）|
| PagedAttention / Block | KV Cache 分页管理；块是分配的最小单位（block_size 个 token）|
| Prefix Caching | 相同前缀复用 KV 块，免重复 prefill |
| Chunked Prefill | 长 prompt 切片多步计算，与 decode 混批 |
| EngineCore | V1 引擎核心（调度+执行循环）所在进程/类 |
| ZMQ | 前端与 EngineCore 的进程间消息库（msgpack 序列化）|
| OOT 插件 | Out-Of-Tree 插件，如 vllm-ascend（不随 vLLM 主干发布）|
| entry_points | Python 包元数据的插件发现机制，vLLM 插件协议的基石 |
| current_platform | 平台层单例，全部设备相关差异的统一出口 |
| ACL / CANN / HCCL | 昇腾计算语言/异构计算架构/集合通信库（对应 CUDA/cuBLAS/NCCL）|
| ACLGraph | 昇腾静态图捕获重放机制（对应 CUDA Graph）|
| torch_npu | PyTorch 昇腾适配层（对应设备后端）|
| P/D 分离 | Prefill/Decode 分离部署（vllm-ascend 支持的 KV 迁移场景）|

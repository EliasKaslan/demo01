# 概览

大语言模型推理的显存瓶颈主要来自三部分：**模型权重**、**KV Cache**、**运行时激活值**。随着模型规模从百亿级增长到万亿级（如 Kimi-K3 的 2.8T 参数），单张 GPU 已无法容纳完整模型，必须通过多种并行技术将计算与存储分散到多卡 / 多节点。

vLLM 作为高性能推理框架，原生支持 **张量并行（TP）、数据并行（DP）、专家并行（EP）、流水线并行（PP）、上下文并行（CP）、序列并行（SP）** 六大并行维度，各维度切分粒度、通信开销、显存收益各不相同，可组合使用以适配不同规模的模型与硬件拓扑。

**核心显存计算公式（BF16 精度）：**

- 模型权重显存 = 参数量 × 2 Byte
- KV Cache 显存 ≈ 2 × batch_size × seq_len × num_layers × num_kv_heads × head_dim × 2 Byte
  - 第一个系数 2 代表 K、V 两份缓存
  - 第二个系数 2 为 BF16 单元素字节数
  - 标准 MHA 架构下 `num_kv_heads × head_dim = hidden_size`，可简化为 `batch_size × seq_len × hidden_size × num_layers × 4 Byte`
- 激活显存 ≈ 权重显存的 10%~30%（推理阶段，随 batch 与序列长度变化）

# 张量并行 TP

## 原理

张量并行（Tensor Parallelism）是**层内并行**策略：将 Transformer 每一层的权重矩阵（注意力的 Q/K/V/O 投影矩阵、FFN 的门控 / 上 / 下投影矩阵）按行或按列切分到多张 GPU 上，每张卡只持有一部分权重，计算时各自完成分片矩阵乘法，再通过 All-Reduce / All-Gather 集合通信拼合结果。

以线性层 `Y = XA` 为例：

- **列并行**：将 A 按列切分为 `[A₁, A₂]`，各卡独立计算 `XA₁`、`XA₂`，最后沿列维度拼接结果
- **行并行**：将 A 按行切分为 `[A₁; A₂]`，输入 X 对应沿列切分，各卡独立计算后通过 All-Reduce 求和得到最终结果

## 作用

- 解决单卡放不下单层权重的问题，将模型宽度维度（hidden_size）打散
- 同节点内通过 NVLink 高速互联，通信延迟低，效率高
- 降低单卡权重显存，释放更多空间给 KV Cache

## vLLM 中使用方式

```python
from vllm import LLM

# 单节点内 8 卡张量并行
llm = LLM(
    model="model-path",
    tensor_parallel_size=8,
)
```

命令行启动：

```bash
vllm serve model-path --tensor-parallel-size 8
```

## 对显存的影响

- **模型权重**：单卡权重显存 ≈ 总权重显存 / TP
- **KV Cache**：默认按 head 维度分片，单卡 KV Cache ≈ 总 KV Cache / TP
- **激活值**：中间激活同样按 TP 分片
- **额外开销**：需预留通信缓冲区，约占权重的 1%~3%

> **注意**：TP 依赖高频集合通信，受限于节点内高速互联，通常不建议跨节点使用，实用上限为单节点 GPU 数（如 8 / 16）。

# 数据并行 DP

## 原理

数据并行（Data Parallelism）是最基础的并行策略：每张卡持有**完整的模型权重副本**，输入数据按 batch 维度拆分到各卡，各卡独立完成前向计算。推理阶段无需梯度同步，仅在请求分发层面做拆分。

## 作用

- 线性提升推理吞吐量，DP=N 则理论吞吐约提升 N 倍
- 实现简单，推理阶段几乎无通信开销（仅请求分发）
- 适合高并发、低延迟要求的在线服务场景

## vLLM 中使用方式

vLLM 通过分布式启动器（torchrun / ray）实现多副本数据并行：

```bash
# 2 副本数据并行，每副本 4 卡 TP
torchrun --nproc_per_node=8 -m vllm.entrypoints.openai.api_server \
  --model model-path \
  --tensor-parallel-size 4 \
  --data-parallel-size 2
```

## 对显存的影响

- **模型权重**：单卡持有完整权重副本，DP 不降低单卡权重显存
- **KV Cache**：各副本独立维护，系统总 KV Cache 随 DP 线性增长
- **适用场景**：当单副本权重已能放入单卡，需要提升吞吐时使用

> **关键区别**：TP 是"切分一个蛋糕大家分着吃"，DP 是"每人一整个蛋糕"。DP 不节省单卡显存，只增加系统总吞吐量。

# 专家并行 EP

## 原理

专家并行（Expert Parallelism）是 **MoE（混合专家）模型专属** 的并行维度。MoE 模型每层包含大量独立的 Expert FFN，前向时每个 token 只路由到少数几个专家。EP 将所有 Expert 均匀分布到多张 GPU 上，每张卡只持有总 Expert 的 1/EP。

计算流程：

1. 路由门控决定每个 token 去往哪些专家
2. 通过 All-to-All 通信将 token 分发到对应专家所在 GPU
3. 各卡独立计算本地专家的 FFN
4. 再次 All-to-All 将计算结果送回原 rank

## 作用

- MoE 模型参数主要集中在专家层，EP 是降低单卡权重显存最直接的手段
- 专家数量越多，EP 的扩展能力越强（如 Kimi-K3 有 896 个路由专家）
- 可与 TP 组合，形成"层内张量切分 + 专家维度切分"的二维并行

## vLLM 中使用方式

vLLM 中 EP 由 TP 与 DP 共同构成，即 EP 并行度 = TP 组内的专家分布 × DP 维度的专家扩展。当使用 MoE 模型且设置了 `tensor_parallel_size` 与 `data_parallel_size` 时，专家并行自动生效：专家层在 TP+DP 构成的组内做 All-to-All 分发，注意力层则保持 DP 行为。

```bash
# 单节点 8 卡，TP=4，DP=2 → EP 并行度 = 8
torchrun --nproc_per_node=8 -m vllm.entrypoints.openai.api_server \
  --model moonshotai/Kimi-K3 \
  --tensor-parallel-size 4 \
  --data-parallel-size 2
```

## 对显存的影响

- **专家权重**：单卡专家权重显存 ≈ 总专家权重 / EP
- **非专家权重**（注意力、嵌入、共享专家、门控等）：按 TP 切分，与 EP 无关
- **通信开销**：每层 MoE 需要两次 All-to-All，通信量与激活 token 数成正比

> **核心价值**：对于 2.8T 参数的 Kimi-K3，专家参数占总参数 95% 以上，EP 是将单卡权重压入 64GB 显存的关键技术。

# 流水线并行 PP

## 原理

流水线并行（Pipeline Parallelism）是**层间并行**策略：将模型按层（Layer）拆分为多个阶段（Stage），每个 GPU 负责连续的若干层。输入数据被拆分为微批次（Micro-batch），像流水线一样依次经过各阶段。

例如 PP=4 时：

- GPU 0 负责第 1 ~ N 层
- GPU 1 负责第 N+1 ~ 2N 层
- GPU 2 负责第 2N+1 ~ 3N 层
- GPU 3 负责第 3N+1 ~ 4N 层

## 作用

- 突破单节点 TP 的规模上限，实现跨节点的超大模型部署
- 通信量远小于 TP（仅传输层间激活，而非每层内部多次集合通信）
- 适合极深模型或跨低带宽节点的场景

## vLLM 中使用方式

```python
from vllm import LLM

llm = LLM(
    model="model-path",
    pipeline_parallel_size=4,
    tensor_parallel_size=8,
)
```

命令行启动（4 阶段流水线 + 8 卡张量并行）：

```bash
vllm serve model-path --pipeline-parallel-size 4 --tensor-parallel-size 8
```

## 对显存的影响

- **模型权重**：单卡权重显存 ≈ 总权重显存 / PP
- **KV Cache**：每阶段只保存自己负责层的 KV Cache，约为总量 / PP
- **额外开销**：需要存储微批次的激活值用于流水线传递
- **副作用**：存在"流水线气泡"，PP 越大气泡占比越高，首 token 延迟上升

> **选型建议**：优先用满节点内 TP，再用 PP 跨节点扩展。PP 适合吞吐量优先、对延迟不敏感的离线 / 批处理场景。

# 上下文并行 CP

## 原理

上下文并行（Context Parallelism）沿**序列长度维度**切分 KV Cache 与注意力计算，让多张 GPU 各自保存并处理序列的一部分。核心解决超长上下文（128K+ tokens）下单卡 KV Cache 爆炸的问题。

解码阶段 CP（DCP）采用交错分片布局：KV Cache 按 token 交错分配到各 CP rank，注意力计算时通过 Ring-Attention 风格的环状通信完成全局注意力计算。

## 作用

- 大幅降低单卡 KV Cache 占用，支持百万级 token 上下文
- Prefill 阶段并行计算长序列，降低首 Token 延迟
- 不切分模型权重，可与 TP / PP 正交组合

## vLLM 中使用方式

```bash
vllm serve model-path \
  --tensor-parallel-size 4 \
  --context-parallel-size 2 \
  --enable-decode-context-parallel
```

## 对显存的影响

- **模型权重**：不切分，单卡权重与 CP 无关
- **KV Cache**：单卡 KV Cache ≈ 总 KV Cache / CP
- **激活值**：序列维度分片，激活显存同步降低
- **通信开销**：每层注意力需要跨 CP rank 交换 KV 块，通信量与序列长度正相关

> **适用场景**：Kimi-K3 原生支持 1M token 上下文，CP 是长上下文推理的必备技术。

# 序列并行 SP

## 原理

序列并行（Sequence Parallelism）同样沿序列维度切分，但与 CP 不同：SP 主要切分**注意力之外的逐元素算子**（LayerNorm、Dropout、残差连接等），配合 TP 使用，消除 TP 中这些算子的冗余复制。

在标准 TP 中，LayerNorm 等逐元素算子需要完整的隐藏态，因此每卡都要保留完整序列的激活值。SP 将序列维度也打散，进一步降低激活显存峰值。

## 作用

- 减少 TP 模式下的激活值冗余存储
- 降低长序列下的中间激活显存峰值
- vLLM 中对 MoE 模型默认开启，配合 MegaMoE 内核优化通信

## vLLM 中使用方式

vLLM 中序列并行通常随 TP 自动启用，无需额外参数，尤其在 MoE 模型 + MegaMoE 内核路径下默认开启。

手动控制可通过环境变量：

```bash
export VLLM_ENABLE_SEQUENCE_PARALLEL=1
```

## 对显存的影响

- **模型权重**：无影响，权重仍按 TP 切分
- **激活显存**：序列维度分片，激活峰值降低为 1/SP
- **KV Cache**：不直接切分 KV Cache（KV 维度由 CP 负责）
- **通信开销**：增加少量 All-Gather / Reduce-Scatter 操作

# 其它并行与优化技术

## Prefill / Decode 分离部署（PD Disaggregation）

将预填充（Prefill）和解码（Decode）拆分为独立实例分别部署。Prefill 计算密集、KV 写入量大；Decode 访存密集、KV 读取频繁。分离后可各自优化并行配置与硬件选型，整体吞吐可提升 2~3 倍。vLLM 支持通过前缀解码后端等参数配置相关能力。

## ZeRO 风格推理显存优化

借鉴训练阶段的 ZeRO 思想，推理时将权重分片存储在各卡，计算时按需 All-Gather。适合超大规模模型权重加载阶段的显存削峰，以及极端显存受限场景。

# Kimi-K3 16 机 × 16 卡部署方案与显存测算

## 模型基础参数

| 参数项 | 数值 |
|--------|------|
| 总参数量 | 2.8T（约 28000 亿） |
| 激活参数量 | 约 104B / token |
| 网络层数 | 93 层（69 层 KDA + 24 层 Gated MLA） |
| 路由专家数 | 896 个 / 层，每 token 选 16 个 |
| 共享专家数 | 2 个 / 层 |
| 权重精度 | BF16（反量化后） |
| 总权重大小 | 2.8T × 2 Byte ≈ **5.6 TB** |
| 上下文窗口 | 1,048,576 token |

## 硬件配置

- 节点数：16 台
- 单节点 GPU 数：16 卡
- 单卡显存：64 GB
- 总卡数：256 卡
- 总显存：256 × 64 GB = 16384 GB = **16 TB**

## 推荐并行拓扑

采用 **PP + TP + EP** 三维组合：

| 并行维度 | 取值 | 说明 |
|----------|------|------|
| PP（流水线并行） | 16 | 跨 16 节点，每节点一个流水线阶段，每阶段约 5~6 层 |
| TP（张量并行） | 2 | 节点内每 2 卡做层内张量切分 |
| EP（专家并行） | 8 | 节点内专家维度 8 路分片，每卡持有 1/8 专家 |
| DP（数据并行） | 1 | 单副本跑满，如需更高吞吐可调整 |

**验证总卡数**：PP × TP × EP = 16 × 2 × 8 = **256 卡** ✓

## 单卡显存详细测算

### 1. 模型权重显存

**每流水线阶段权重** = 总权重 / PP = 5.6 TB / 16 = **350 GB**

权重分为两部分：

- **非专家部分**（注意力层、嵌入、输出头、共享专家、门控等）：约占总参数 5%，即 17.5 GB / 阶段
- **专家部分**（896 个路由专家）：约占总参数 95%，即 332.5 GB / 阶段

**单卡非专家权重** = 17.5 GB / TP = 17.5 / 2 = **8.75 GB**

**单卡专家权重** = 332.5 GB / EP = 332.5 / 8 = **41.56 GB**

**单卡权重合计** = 8.75 + 41.56 = **50.31 GB**

### 2. KV Cache 显存

假设并发 32 请求，平均上下文 32K tokens，BF16 KV Cache。

> 注：Kimi-K3 采用 KDA + Gated MLA 混合注意力架构，以下按标准 Transformer 公式做保守估算（hidden_size 取经验估算值 8192，每阶段约 6 层）。

单阶段 KV Cache 总量 ≈ 2 × batch × seq_len × layers_per_stage × hidden_size × 2 Byte
= 2 × 32 × 32768 × 6 × 8192 × 2 Byte ≈ **24 GB / 阶段**

**单卡 KV Cache** = 24 GB / TP = 24 / 2 = **12 GB**

### 3. 激活与运行时开销

- 前向激活缓冲区：约 1~2 GB
- 通信缓冲区、PagedAttention 元数据：约 0.5 GB
- 合计：约 **2 GB**

### 4. 单卡显存汇总

| 项目 | 显存占用 |
|------|----------|
| 模型权重（BF16） | 50.31 GB |
| KV Cache（32 并发 × 32K） | 12 GB |
| 激活与运行时开销 | ~2 GB |
| **合计** | **~64.31 GB** |

> **说明**：上述配置下显存接近满负载。实际生产中建议：
> 
> - 降低并发数或缩短平均上下文，将 KV Cache 控制在 8 GB 以内
> - 开启 FP8 KV Cache 量化，KV 显存可减半至约 6 GB
> - 预留 5%~10% 显存余量，设置 `--gpu-memory-utilization 0.9`

## 优化方案：引入 CP 支持长上下文

若需支持 128K 甚至 1M token 上下文，可在上述基础上增加上下文并行，调整为 PP=16, TP=2, EP=4, CP=2（总卡数仍为 256）：

- 权重显存不变（CP 不切权重）
- KV Cache 单卡占用降低为 1/CP，百万 token 场景下仍可容纳
- 代价是注意力计算时增加环状通信开销

# 各并行技术对比总结

| 维度 | 切分对象 | 主要作用 | 单卡权重显存 | 单卡 KV 显存 | 通信开销 | 推荐规模上限 |
|------|----------|----------|-------------|-------------|----------|-------------|
| **TP 张量并行** | 层内权重矩阵 | 层内加速、降低单卡权重 | ÷ TP | ÷ TP | 高（每层多次 All-Reduce） | 单节点内 8~16 |
| **DP 数据并行** | Batch 维度 | 提升系统总吞吐量 | 不变 | 不变（各副本独立） | 极低 | 可横向扩展 |
| **EP 专家并行** | MoE 专家 FFN | MoE 模型降单卡权重 | 专家部分 ÷ EP | 不变 | 中（每层两次 All-to-All） | 不超过专家总数 |
| **PP 流水线并行** | 层（Layer） | 跨节点扩模型规模 | ÷ PP | ÷ PP | 低（仅阶段间传激活） | 不超过总层数 |
| **CP 上下文并行** | 序列 / KV Cache | 支持超长上下文 | 不变 | ÷ CP | 中（注意力层环状通信） | 8~32 |
| **SP 序列并行** | 激活序列维 | 降低激活显存峰值 | 不变 | 不变 | 低 | 随 TP 自动启用 |

**选型原则**：

1. 单节点内优先用 **TP** 吃满 NVLink 带宽
2. MoE 模型必须配合 **EP** 控制单卡权重
3. 跨节点扩展用 **PP**，通信量最小
4. 超长上下文场景加 **CP**
5. 需要高吞吐量再加 **DP**
6. 各维度正交组合，总卡数 = PP × TP × EP × DP
